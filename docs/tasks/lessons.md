# 经验与教训

- 用户反馈“布局仍然很大”时，不能只继续缩字号或 padding；必须同时测量容器实际高度、首屏后续内容露出量，并核对 CSS Grid 中相互覆盖的列是否被自动排到不同网格行。视觉叠放必须显式声明行关系，避免结构错误伪装成设计留白。
- 用户提供真实窗口截图后，不能继续用 1440px 计算字号上限证明“已经不大”；必须在用户实际宽屏比例下检查同屏视觉占比、书法字体墨量和换行形态。展示字的 CSS 像素只是输入，画面占比才是验收结果。
- 浏览器验收不能只检查无报错、无横向溢出或 DOM 已挂载；凡是入场揭示内容，都必须在滚动进入视口后断言计算样式已回到可见终态，并覆盖遮罩、子项和真实媒体。
- 大胆排版必须分别约束装饰字与承载信息的真实标题：装饰字可以裁切越界，真实标题仍需设桌面与移动端尺寸上限，不能让“视觉冲击”破坏阅读与内容密度。
- 用户要求“真正大胆”时，不能只把既有网格中的标题、编号、错位和 hover 分别加码；先检查去掉文案后的页面骨架是否仍有独特观看机制，再用一个统领全站的结构动作重做入口与章节接棒，并用真实浏览器首屏和跨页连续性证明差异。
- 线上页面持续加载且本机 TLS 工具异常时，先同时核对部署配置与独立网络结果；用户指定回退基线后立即停止原排查路径，精确核对目标提交和差异，再按指定基线重新验证。
- 用户明确要求远程同步回退时，先 fetch 固定远程现状，再用 `--force-with-lease`，推送后同时核对远程 SHA 与部署工作流状态。
- 用户重启系统后故障仍在，不能继续把“重启”当作结论；应把所有资源统一报 `ERR_CERT_DATABASE_CHANGED` 视为系统 TLS 基础设施故障，建立跨域 Schannel 反馈并查明持久配置或后台变更源。
- 用户确认 Edge 正常、Chrome 失败后，应立即把浏览器差分置于 Schannel 线索之前；命令行 Schannel 故障可能并存，不能据此把 Chrome 独有故障直接归因到全局系统 TLS。
- 对约定为硬链接的规则文件，不能只比较内容或沿用旧记录；应使用 `fsutil hardlink list` 核对当前文件关系。链接断开且用户指定主文件后，以主文件重建链接，再验证两个路径的文件 ID、哈希与 Git 差异。
- 用户询问网站“还缺什么”时，应先按其语境限定审查维度；用户明确只谈设计后，不再扩展到功能、产品流程或技术栈，只从构图、层级、色彩、字体、留白、图像与视觉节奏给出建议。
- 用户指出“有粒子但不明显”时，不能把 DOM 中存在动画当作视觉完成；应给出首屏可见数量、尺寸、透明度与观察时限等验收条件，并通过真实浏览器截图或录屏判断是否达到预期。
- 用户要求“建新分支提交改动”时，须先区分改动性质再定归宿：特性工作进分支，全仓基线类提交（行尾统一、格式化基线、CI 配置）应直接落在主分支，避免基线生效依赖特性分支的合并顺序。被纠正后用 cherry-pick 到主分支 + `rebase --onto` 从特性分支移除，并核对两侧文件归属与工作区行尾。
